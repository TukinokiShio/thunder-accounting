# 安卓端四板块布局 —— 第一性原理分析与重排方案

> 日期：2026-09-13 · 依据：本机安卓模拟器实测（412×915 CSS px）+ 源码逐行取证
> 本文只写**可被证明的结论**。凡是不能证伪的审美偏好，一律不作为改动依据。

---

## 一、从用户目标反推，而不是从现有界面反推

记账工具存在的唯一理由：**让「钱花去哪了」这件事变得可回答。**

它由两个不可再分的动作构成：

| 动作 | 频率 | 要求 |
|---|---|---|
| **记一笔**（输入） | 高频 | 要快、要轻、单手可完成 |
| **看明白**（回顾） | 高频 | 先给结论，再按需下钻 |

平台约束（实测值，不是估计）：

- 可用内容宽 **348px**；首屏可用内容带 **711px**
  （= 915 − 顶栏 88 − 上下内边距 36 − 底部导航 80）
- 单手拇指可达区在下半屏
- **无硬件返回键可用**：本应用是零 history 的 SPA（全库无 `pushState` / `popstate` / 路由），
  Capacitor 仅在 `canGoBack()` 为真时才回退 → 返回键是空操作

由此得到唯一评价标准：

> **每个板块要么在 711px 内交付一个「用户当场要的答案」，要么必须给出明确的下一步去向。
> 任何既不给答案、也不给去向的界面元素，都是纯成本。**

## 二、用这个标准量现状（全部为实测值）

| 板块 | 实测现状（门禁基线 `470395c` 量测） | 结论 |
|---|---|---|
| 首页 | 6 张卡在 412px 下退化为**单列**（`grid-cols-1`），实测堆叠 **800px**（单卡 120px） | ✗ 不好用 |
| 账单 | 筛选区占 **232px = 首屏 32.6%**；首屏只剩 **4 条**；列表行**分类名文字列仅 60.6px**，溢出后被 `overflow-hidden` **裁切** | ✗ 功能受损 |
| 统计 | **8 张卡**、实测 **2573px ≈ 3.2 屏**；图表动画跑 **1500ms × 3**；同一「总支出」最多出现在 **5 处**；Legend 与紧邻小表重复渲染同一组分类名+百分比 | ✗ 冗余 |
| 分类管理 | **无任何可见返回路径**（门禁 A6 断言"不存在"通过）；硬件返回键空操作；底部「我的」Tab 已高亮 → **进去出不来** | ✗ **存在性缺陷** |
| 个人中心 | 5 个 Tab 里 **3 个**为空壳（门禁 A8 断言"3 个仍在"通过）；左栏导航占首屏约 **186px（26%，调研估算）**；语言切换器存在但入口被隐藏 → **安卓完全无法切语言**（A7 断言"点安全设置无切换器"通过） | ✗ **存在性缺陷** |

> ⚠️ **本表的两个数字曾被我写错，已按门禁实测更正**：
> 账单首屏我原写 **6 条**，实测 **4 条** —— 6 条来自 spike 的**理想行高 69px**，
> 而真实行高是 **83~99px**（60px 列宽把分类名挤成 2~3 行）。**我的数字偏乐观。**
> 统计页我原写 **2702px ≈ 3.8 屏**（调研估算），实测基线 **2573px ≈ 3.2 屏**。
> 相关教训见第五节「模型 vs 实测」。


**关键区分**：第 1~3 行是「不好用」，第 4~5 行是「不能用」。
用户说「整体上不满意」，但底下是两类不同性质的问题 —— **前者掺品味，后者可证明。**
所以本方案只改**可以被证明**的部分。

## 三、逐条推导

### 1. 首页：6 张卡单列 → 一行两卡

- 单列下 6 张卡各约 96px + 间距 ≈ **630px**，几乎吃掉整个首屏；而每张卡只装「一个标签 + 一个数字」。
- 单卡信息量（label 12px + value 18px + detail 12px）在 **约 170px** 宽下完全放得下 ——
  `¥1,234.56` 在 `text-lg`（18px）下实测约需 110px。
- → 一行两卡把 6 卡占高从 ~630px 降到 **~330px**，首屏能同时容纳全部 6 张卡**加上最近记录的开头**。
  **信息量未减，空间砍半。**

### 2. 账单：把低频动作从常驻位置撤下来

- 手机上**筛选是低频动作**（多数时候用户只是「扫一眼最近账单」），
  但当前 6 个筛选控件**永久占掉首屏 32.6%**，且无任何折叠能力。
- 列表行的**核心信息是分类 / 金额 / 日期**。编辑与删除是低频动作，
  但当前两个 **44px 按钮 + 4 处 `gap-4`** 把中部文字列挤到仅 **约 45px** →
  「分类1 · 分类2」在 `text-sm` 下需要约 95px，**溢出后被卡片 `overflow-hidden` 裁掉**。
  **用户看不全自己记的分类名 —— 这是功能性损失，不是审美问题。**
- → 改：筛选默认收起为一行「当前筛选状态」，点击展开（渐进披露）；
  编辑/删除移入长按菜单或左滑。
- → 预期：首屏 **6 条 → ≥9 条**，分类名完整可读。

### 3. 统计：重复不等于信息量

- 现状把**所有切片平铺**：2 个环形图 + 1 个折线图 + 3 张表。
- 同一次 `getStats` 的返回被渲染了 **3 遍**（两个 Legend + 两张小表 + 一张全量表）；
  同一金额最多出现 **5 处**。用户没有获得 5 倍信息，只是被迫滚 3.8 屏。
- 图表高度**硬编码 240 / 240 / 260 = 740px 固定**，不随视口变化 —— 在小屏上占首屏的 **104%**。
- 动画 **1500ms**：项目自己已有约定 `CHART_ANIM_DURATION = 300`
  （`StatCardDetailDialog.tsx`），`Stats.tsx` 是唯一未统一处 —— 项目踩坑记录第 10 条已写明。
- → 改：收敛为 **结论（汇总 + 环比）→ 分解（一个环形图，占比由 Legend 承载，删掉重复小表）
  → 趋势（折线）→ 明细（默认折叠）**。二级下钻由「常驻第二个环形图」改为「点击一级分类才展开」。
- → 预期：**3.8 屏 → ≤2 屏**，动画 300ms。

### 4. 分类管理：先修「出不去」

这是唯一一个**不修就不能上线**的问题：

- 页头只有标题 + 编辑开关，**无返回箭头**（全库 `ArrowLeft` 只出现在 `Login.tsx`）。
- 即使渲染关闭按钮也不会工作：`App.tsx:79` 传入的 `onClose` 是空函数。
- 硬件返回键 = 空操作（零 history）。
- 底部「我的」Tab 在此时**已经高亮**（`AndroidTabBar.tsx:34` 专门写了
  `activePage === 'categories'` 时高亮 profile）→ **连「再点一次回去」都被视觉否定了。**

→ 改：页头加明确返回路径；空态文案与布局对齐
（现仍写「从左侧选择一个分类进行编辑」，而窄屏早已改为上下堆叠）；
编辑模式的拖动/删除**只在编辑模式内可用**这条已实现且正确（用户此前明确要求），
但**发现性为零** —— 「拖动排序」只存在于 `aria-label`，页面上无任何可见提示 → 补可见提示。

### 5. 个人中心：按「本机能提供什么」裁剪，而不是渲染后再短路

- 纯本地模式下，「安全设置 / 绑定管理 / 危险操作」对应的是**云端能力，根本不存在**。
  现在渲染一个空壳 + 一句「本版本不可用」= 让用户点进 3 个死胡同。
- 左栏导航占 **186px（首屏 26%）**，而 3 个 Tab 的正文各只有 **52px**
  → **导航比内容重 3.5 倍。**
- → 改：本地模式下这三个 Tab **整个不渲染**（而非渲染后短路），导航随之收缩；
  同一栏内补上 **「设置」入口**（这是语言切换的唯一出口）、分类管理、关于。
- → 顺带修：账号ID 因 `accountId` 恒空而永久显示占位符「加载中...」；
  本地模式下「退出登录」点击会抛错、只留一个 toast；死代码组件 `CloudUnavailableNotice`。

## 四、明确不做（非目标）

| 项 | 理由 |
|---|---|
| **不翻译预设分类名**（餐饮食品 / 交通出行 …） | 它们是**持久化在 SQLite 里的用户数据**，不是 UI 文案。翻译会破坏已有账单的分类一致性。这是有意划出的边界。 |
| 不改 i18n 机制（zh 返回 key / en 查词典） | 机制本身正确，问题在**覆盖不全**，只补内容。 |
| 不改桌面端 | 移动端样式一律走 `html.platform-android` 选择器（桌面零命中），平台分支走 `isAndroid()`。 |
| 不做横屏适配 | 首版不做，属范围外。 |

## 五、验收标准与实测结果（门禁两侧对照）

> **本表已全部换成实测值。**先前版本里我写的是模型估算，其中至少两个数字经实测证明是**错的**。
> 教训记录在下方「模型 vs 实测」。

| # | 指标 | 基线实测 | 目标 | 主树实测 | 判定 |
|---|---|---|---|---|---|
| A1 | 账单首屏完整可见条数 | **4** | ≥9 | **11**（行高 56px） | ✅ |
| A2 | 账单列表分类名文字列宽 | **60.6px** | ≥200px 且不裁切 | **268px** | ✅ |
| A3 | 统计页整页高度 | **2573px** | ≤1400px | **1327px** | ✅ |
| A4 | 图表动画时长 | **1500ms × 3**（未设置） | 300ms | **2 个图表均 300**，无 1500 泄漏 | ✅ |
| A5 | 首页 6 卡占高 | **800px**（单卡 120px） | ≤340px | **323px**（单卡 97px，2 列） | ✅ |
| A6 | 分类管理返回入口 | **不存在** | 存在且回「我的」 | 点击 → `profile` | ✅ |
| A7 | 安卓语言切换可达 | **不可达** | 从「我的」可达 | 点「设置」→ 切换器 + `aria-pressed` 翻转 | ✅ |
| A8 | 「我的」空壳 Tab | **3 个仍在** | 0 | **3 个消失** | ✅ |

**两侧对照**：基线 worktree（`470395c`）**9/9 FAIL**（退出码 1，连跑 2 次一致）；
主工作树 **9/9 PASS**（退出码 0，连跑 2 次一致）。
**负对照是门禁有效性的唯一证据** —— 一个在旧设计上也"通过"的门禁，等于没有门禁。

```
npm run verify:android-layout                                    # 正对照
node scripts/verify-android-layout.cjs --root ../ta-gate-baseline # 负对照
```

**实现要点**：探针页 = 真 `src/` 组件 + 真构建 CSS，412×915 无头 Chromium，
`file://` 自包含单页（CSS/JS 全内联 —— 沿用 `verify-modal-scope` 的"同进程 http 会死锁"结论），
`window.electronAPI` 换成确定性内存夹具。**断言一律不看 class**（文本定位 + 最小公共祖先 + 计算样式），
所以同一条断言能同时表达新旧两种 DOM。
三条环境自检（`platform-android` 已加 / `android.css` 确已生效 / **合成点击能驱动 React**）任一不成立即退出码 2 ——
否则 A6/A7 会假失败，或在桌面布局上量出"安卓通过"。

### 模型 vs 实测：三次分歧，实测全胜

| 指标 | 我的结构模型 | 实施者模型 / 外推 | **门禁实测** |
|---|---|---|---|
| 统计页整页高度 | ~1150px | 1610px | **1327px** |
| 首页 6 卡占高 | ~630px（基线） | 253px（改后） | **800px（基线）→ 323px（主树）** |
| 账单首屏条数 | 6（引自 spike） | 10（改后） | **4（基线）→ 11（主树）** |

- 统计页那次争论：1610 vs 1150 vs 实测 **1327** —— 我偏差 15%，对方偏差 22%，**双方都没量对**。
- 首屏条数更关键：我引用的 6 条来自 spike 的**理想行高 69px**，而**实测行高 83~99px** ——
  60px 的列宽把分类名挤成 2~3 行，真实基线只有 **4 条**。我的数字**偏乐观**。
- 但反过来：**如果没有那次"拒绝凭推算压缩"的裁决，就会依据 1610px 这个错数字去牺牲图表可读性**（`200→160`）。
  **结论：几何量上的模型只能用来排序候选方案，不能用来判定结果或设定阈值。**

### 测量口径（两个并存，必须显式声明）

| 口径 | 值 | 定义 |
|---|---|---|
| 我的 | **711px** | `视口高 915 − 顶栏 88 − 页面内容上内边距 36 − 底部导航 80` |
| 门禁实现方 | **795px** | 「用户真实可见」口径；精确定义**待其给出可复算边界**（差异疑来自是否计入 `.aurora-main` 的 padding 与底部遮挡算法） |

内容宽同样有两个：真机 **348px**、无头 Chromium **342px**（`scrollbar-gutter` 实占 6px）。
**口径差不影响 A1**：A1 是**经验计数**（数完整可见的行），不是由阈值推算的 —— 阈值只用于比较，不参与测量。

### 已知边界（不掩盖）

1. **系统返回键不退出分类管理的编辑模式**：编辑模式是 `CategoryManager` 的组件内 state，
   未提升到 store，因此系统返回直接回「我的」而非先退出编辑模式。本轮**有意不做** ——
   需要解冻刚稳定的 store，代价大于收益。真机验收时留意是否别扭。
2. **系统返回键本身无法在 jsdom / 无头 Chromium 中驱动**，只能真机验证（三条验收路径见 `docs/android-acceptance.md`）。


### 测量纪律（本轮新增，来自一次实际分歧）

指标 3 出现了 **1610px vs 1150px** 两个独立估算、相差 460px。原因是其中一方把
「实测 2702 ÷ 模型 1776 = 1.52」当作**统一缩放因子**去外推改后结构 —— 这**在方法上不成立**：

- **不随行高/字体模型缩放**的量：图表固定高度（240→200）、整卡默认不渲染（→ 0）、
  Legend 节点消失、卡片折叠 —— 其中「整卡消失」在减量里占最大头，被凭空放大 52%
- **随行高缩放**的量：文字行、表格行、卡片 padding
- 把同一个因子乘到两类不同量纲上 → 系统性偏大

**因此确立两条纪律**：

1. **差值优于绝对值**。固定 px 项在两个模型里是同一批确定值，所以
   「改前 → 改后」的**差值**比绝对高度稳健；而基线 2702px 是**实测**的 →
   `2702 − 真实差值` 比任何绝对模型都准。门禁因此输出
   `基线实测 | 当前实测 | 差值` **三元组**，把门禁从「断言」升级为「诊断」。
2. **不拿可读性换不可信的数字**。据此否决了「图表 200→160」与「折线图折叠」两个提案：
   前者用可读性换一个来源可疑的阈值，后者等于砍掉「看明白钱花去哪了」这个唯一目的的一半。

### 一个覆盖缺口（本轮发现）

`src/pages/Home.test.tsx` 的 12 条断言**全是文本 / 可访问角色 / 弹窗行为**，
**没有一条碰 class 字符串或列数**。而 **jsdom 没有布局引擎** ——
所以「412px 下首页退化成单列」这个真实缺陷，单测**在原理上就抓不到**，历史上也确实没人报过。

→ **结论**：几何类契约（列数 / 高度 / 宽度）只能靠**行为级门禁**（无头浏览器）
或**源码级字符串断言**守住。首页 6 卡的列数与占高，其唯一行为级覆盖就是门禁第 5 条。

## 附：与「中英文混用」的关系

混用与本方案是两个独立根因，但**共用同一条修复纪律**：

1. 默认语言取 `navigator.language`（安卓模拟器为 en-US）→ 首启即英文；
2. i18n 只做**部分覆盖**（451 行中文未走 `t()`）→ 任何非 zh 语言都会暴露漏网。

修 1 会让「zh 用户首启看到全中文」，但**只要 2 还在，换任何语言都会再次混用**。
因此 2 必须用**可执行门禁**闭环（源码级契约测试），而不是靠人工清点 ——
否则新增一个界面就会重新引入一批漏网。
