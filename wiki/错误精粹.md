# Thunder Accounting 项目错误精粹

> 已收录 6 条项目专属、已验证的错误条目（KI-2026-09-12-003 已于 v1.17.6 补入作用域替身修正与回归复验；2026-09-13 新增 001~003 三条安卓构建相关条目）。

### KI-2026-09-12-001｜工作区 package.json 结构被截断导致无法构建打包

- domain: build / 版本与打包
- severity: P0
- env: Windows + git-bash；thunder-accounting 仓库根
- valid_since: 2026-09-12
- last_verified: 2026-09-12
- status: active
- root_cause: 工作区 `package.json` 的 `scripts`、`devDependencies`、`build` 三段被删除（且未提交，`git status` 显示 ` M package.json`）。此时 `npm run build` / `npm run dist:win` / `npm test` 全部不可用，electron-builder 也读不到 `build` 字段。疑似上一轮某个「生成精简 package.json」的操作误写到了仓库根。
- prevention:
  1. 每轮开始与版本号改动前后，执行 `git diff package.json`，确认**只出现 version 行差异**；
  2. 任何"精简/裁剪 package.json"的操作必须写入构建产物目录（如 `app-out/`、`release/win-unpacked/`），**禁止**写入仓库根；
  3. 发现结构缺失时用 `git show HEAD:package.json` 为基准恢复，不要手写重建。
- evidence: `git diff package.json` 显示删除 `scripts`（15 行）、`devDependencies`（15 行）、`build`（25 行）；恢复后 `git diff` 仅剩 `-  "version": "1.16.9"` / `+  "version": "1.17.0"`。
- revalidation: 修复后 `npm run dist:win` 与 `npm test` 均正常，263 用例通过。

### KI-2026-09-12-002｜Inno `UsePreviousAppDir` 默认 yes 使静默安装落到历史目录而非 DefaultDirName

- domain: build / Inno Setup 交付
- severity: P1
- env: Inno Setup 6（`E:\SHIO\inno\Inno Setup 6\ISCC.exe`）；`scripts/thunder-setup.iss`
- valid_since: 2026-09-12
- last_verified: 2026-09-12
- status: active
- root_cause: `[Setup]` 未设置 `UsePreviousAppDir`，而 Inno 的默认值是 **yes** —— 静默升级时会读取注册表 `HKCU\...\Uninstall\{AppId}_is1` 下的 `InstallLocation` 并沿用该目录，**完全忽略 `DefaultDirName`**。本项目中历史安装目录是 `雷霆记账app\_exe`，因此新版本被静默装入旧目录，而 AGENTS.md 规定的固定验收目录 `exe\` 保持旧版本（`exe\resources\app.asar` 仍为 1.16.9）。
- prevention:
  1. `.iss` 的 `[Setup]` 显式加 `UsePreviousAppDir=no`（已落地）；
  2. 静默安装**必须**验证实际落点，不能只看 `INSTALL_EXIT=0` —— Inno 装到错误目录同样返回 0；
  3. 验证三件套：`exe\resources\app.asar` 内 `package.json` 的 version、注册表 `DisplayVersion` + `InstallLocation`、桌面/开始菜单快捷方式时间戳；
  4. 需要临时强制落点时可用命令行 `/DIR="<绝对路径>"`（优先级高于 UsePreviousAppDir）。
- evidence: 首次静默安装 `INSTALL_EXIT=0` 但 `exe/resources/app.asar` mtime 仍为 2026-09-08、version 仍为 1.16.9；`find ... -name app.asar -newermt "2026-09-12 16:00"` 定位到实际被写入的是 `雷霆记账app/_exe/resources/app.asar`（version 1.17.0）。
- revalidation: 加 `UsePreviousAppDir=no` 后重编 ISCC 并静默安装（**不传 /DIR**），`exe\resources\app.asar` version = 1.17.0，注册表 `DisplayVersion=1.17.0`、`InstallLocation=E:\Code\CodeProduct\thunder-accounting\exe\`，桌面与开始菜单快捷方式均于 16:16 重建。

### KI-2026-09-12-003｜弹窗遮罩 position:fixed 顶部未铺满（约 24px 露白）

- domain: ui/modal-overlay
- severity: P1
- env: Electron 33 + React 18 + TailwindCSS 3.4（Windows，窗口 1100×720，DPR 1.25）
- valid_since: 2026-09-12
- last_verified: 2026-09-12
- status: active
- root_cause: **未定位到具体属性。** 弹窗全部祖先（`.aurora-shell` / flex-col 容器 / `main.aurora-main` / `.page-viewport` / `.page-frame` / `.page-view`）均无 `transform` / `filter` / `backdrop-filter` / `will-change` / `contain` / `perspective` / `isolation` / `opacity<1` / `zoom`，顶栏也无 z-index —— 按规范 `fixed` 本应以视口为包含块铺满，与实际矛盾。**修复有效性反证了因果**：改为 Portal 到 `document.body` 后现象消失，说明确有祖先在改写包含块，只是未能静态定位。曾被怀疑的 `body { display:flex; align-items:center }` 已用真实构建 CSS 复现证伪。
- prevention:
  1. 模态层（遮罩 + 面板）一律 `createPortal(..., document.body)`，并用**内联样式**写死 `position: fixed` 与四边 0，不用 `fixed inset-0` 工具类；
     **但必须同时带上「作用域替身」**：`class="aurora-shell aurora-portal-root [dark]"` + `data-theme`，并在 CSS 补
     `.aurora-shell.aurora-portal-root { width: auto; min-height: 0; background: transparent; }`。
     原因：Portal 只改变**节点位置**，不搬运**依赖祖先的上下文**。本项目 v1.17.3/v1.17.4 只做了 Portal，
     导致 ① `.aurora-shell .add-bill-dialog` 的 `width/min-height/flex` 版式规则全部失配（弹窗随内容塌缩）
     ② `.dark` token 与 `tailwind darkMode:'class'` 的祖先要求失效（深色主题下弹窗仍浅色）。
     覆盖规则不可省：删掉它替身根会取到 `--bg` 与 `min-height:100%`，整屏盖住应用（已由独立审查证伪确认）。
  2. z-index 分层预留：应用内容 50~60 → 模态 9000 → 第三方 Portal（react-select = 10000）在其上；
  3. **本项目 5 个模态已于 v1.17.4 全部 Portal 化**（`AddBillDialog` / `SettingsDialog` / `CategoryManager` z-index 50→9000，`ConfirmDialog` 60→9500 以保证压在其它模态之上），并于 v1.17.5 统一补上作用域替身；`src/components/modal-portal-contract.test.ts` 是源级契约测试（模态清单**从文件系统派生**，新增模态自动纳入），`npm run verify:modal-scope` 是行为级回归门禁；
  4. 用户报「没铺满 / 露白 / 偏了」时不要目测：用 Pillow 从截图逐像素量出边界坐标与压暗倍率（浅色基准 `--bg #f4eee4`×0.6≈143、`--bg-card #fffaf2`×0.6≈150），把主观描述变成可判定数字；
  5. 复现优先用 headless Chromium + `python -m http.server` + Pillow；本沙箱 Electron 无法启动。
- evidence: commit `8dfa8bf`（修复）+ `61f4501`（前置 perf）；`findings.md` v1.17.3 章节；项目 `artifacts/repro-overlay/`（复现设施与截图）
- revalidation: 2026-09-12 —— v1.17.2 复现缺陷（用户截图量化：全宽转折线 y=101 = 视口顶下方约 24 CSS px，金色按钮被横切、下半精确 40% 压暗）；v1.17.3 修复后以同一方法复验：金色按钮**饱和金像素 287 → 1**（杂点），网页视口内自 y=72 起连续为 150 且无转折，确认已铺满。剩余 y=0~70 未压暗 = Windows 原生标题栏 + 菜单栏，位于渲染进程之外、CSS 物理不可覆盖，属正常。


- regression_repro（2026-09-12 v1.17.5/v1.17.6）：只做 Portal 会在同类项目里引入两处**用户可见回归** ——
  ① 记一笔弹窗**选择分类后塌缩**（未选时面板宽 383px、选中后 310px）；② **深色主题下弹窗仍是浅米色**
  （与 `.dark` token 失配）。修复 = 给模态根加「作用域替身」+ CSS 覆盖规则。
  证据（真实构建 CSS + headless Chromium，含负对照）：无替身时面板宽随内容 250→308（极差 58）且深色面板
  `rgb(255,250,242)`；有替身时恒为 448px（=28rem，极差 0）且深色面板 `rgb(32,34,36)`；四组遮罩四边几何全为 0
  （v1.17.3 的铺满修复未回退）。像素级复核：底板主导色 `rgb(255,250,242)`→`rgb(32,34,36)`、宽度 330px（内容驱动）→446px（规则驱动）。
  该量测已固化为可执行门禁 `npm run verify:modal-scope`（1.3s，含「负对照必须复现」自检）。
- cross_check：`.aurora-shell` 的后代规则**零个**使用 `> + ~` 组合器 → 把 shell 从「祖先」改为「根本身」对后代命中**严格等价**，
  即替身方案与 Portal 之前行为一致（由独立 Reviewer 与独立 Judge 分别复核）。
- related:- related: 生态库 `KI-2026-09-12-003`（同一条目的生态版）+ `KI-2026-09-12-004`（像素量化定位方法）

### KI-2026-09-13-001｜Capacitor 8 安卓构建的 Gradle/AGP 版本必须随宿主框架重新对齐，不能照搬 skill 固化值

- domain: build / Android 打包
- severity: P1
- env: Windows + git-bash；`android-packager` skill；Capacitor 8.5.2；JDK = Android Studio JBR 21.0.10
- valid_since: 2026-09-13
- last_verified: 2026-09-13
- status: active
- root_cause: `android-packager` skill 固化的「Gradle 8.10.2 + AGP 8.5.2」是在**纯 AGP 空 demo** 上验证的。Capacitor 8.5.2 生成的原生工程实际要求 **Gradle 8.14.3 + AGP 8.13.0 + compileSdk/targetSdk 36 + androidx.webkit 1.14.0 + androidx.coordinatorlayout 1.3.0**。本机 Gradle 缓存里只有 AGP 8.5.2，**完全用不上**；若直接照搬 skill 的版本，构建会在插件解析阶段失败。**版本要求由宿主框架决定，不由 skill 决定。**
- prevention:
  1. **每次上手新宿主框架，先读 `android/variables.gradle` + `android/build.gradle` + `gradle/wrapper/gradle-wrapper.properties` 三个文件确认真实要求**，不要照搬 skill 或历史值；
  2. skill 中**只有 JDK 选型是跨项目稳定的**（必须用 JBR 21，禁用系统 JDK 24）；Gradle/AGP/SDK 版本一律现查；
  3. `androidx.webkit` / `androidx.coordinatorlayout` 是 Capacitor 引入的**新增**依赖，本机 Gradle 缓存原本没有（原本只有 25 组 androidx），必须联网补；
  4. 排错顺序：先看 wrapper 要哪个 Gradle → 再看 build.gradle 要哪个 AGP → 最后看 variables.gradle 要哪些 androidx。
- evidence: `aapt2 dump badging app-debug.apk` → `compileSdkVersion='36' targetSdkVersion:'36'`；`android/build.gradle:10` → `classpath 'com.android.tools.build:gradle:8.13.0'`；`gradle-wrapper.properties` → `gradle-8.14.3-bin.zip`；本机 `~/.gradle/caches/modules-2/files-2.1/com.android.tools.build/gradle/` 仅 `8.5.2`
- revalidation: 2026-09-13 —— 按 Capacitor 真实要求（Gradle 8.14.3 + JBR 21）构建空工程：`BUILD SUCCESSFUL in 3m 14s`，`GRADLE_EXIT=0`，APK 4.0MB；安装到 `Pixel_8`（API 37）`Success`，`topResumedActivity=com.thunderspike.demo/.MainActivity`，崩溃日志为空，截图确认 WebView 正常渲染（非白屏）

### KI-2026-09-13-002｜Gradle wrapper 默认拉 `-all` 发行版（≈230MB）造成"构建假死"；国内镜像可用性实测

- domain: build / 网络与镜像
- severity: P2
- env: Windows + git-bash；Gradle wrapper；中国大陆网络
- valid_since: 2026-09-13
- last_verified: 2026-09-13
- status: active
- root_cause: `gradle-wrapper.properties` 默认 `distributionUrl` 指向 `-all` 发行版（约 230 MB，含源码与文档）。在 `services.gradle.org` 上实测 **22 分钟仅下载 77 MB**，且因为命令里用了 `| tail -60`，**中间输出被吞掉**，从外部看完全像"卡死"。实际仍在下载。
- prevention:
  1. **改成 `-bin`（131 MB）**：`distributionUrl=https\://mirrors.cloud.tencent.com/gradle/gradle-8.14.3-bin.zip`；
  2. **镜像可用性实测（2026-09-13）**：`mirrors.cloud.tencent.com/gradle/` ✅ 200；`mirrors.huaweicloud.com/gradle/` ✅ 200；`mirrors.aliyun.com/gradle/` ❌ 404（**不要照抄**）。两个可用镜像与官方的 `Content-Length` 完全一致（`137393837`）→ 同一份文件，可安全替换；
  3. **长任务不要接 `| tail`**：会吞掉全部中间输出导致无法监控。应 `> build.log 2>&1` 落日志，再读日志判断进度；
  4. 判断"在下载"还是"卡死"：看 `~/.gradle/wrapper/dists/<dist>/<hash>/*.part` 的**体积是否增长**；
  5. Maven 依赖同步加速：在根 `build.gradle` 的 `buildscript` 与 `allprojects` **两处** `repositories` 前置 `maven.aliyun.com` 的 `google` / `public` / `gradle-plugin` 镜像，**保留 `google()` / `mavenCentral()` 兜底**。
- evidence: `-all` 部分下载 79 MB 后清理；换镜像 + `-bin` 后 `Downloading ... 100%` 瞬间完成；`build.log` 记 `BUILD SUCCESSFUL in 3m 14s`
- revalidation: 2026-09-13 —— 换镜像后完整构建通过（见 KI-2026-09-13-001 的 revalidation）

### KI-2026-09-13-003｜沙箱内无法跑 Maven 依赖解析与 Android 模拟器

- domain: 本机环境 / 沙箱边界
- severity: P1
- env: Windows + git-bash；WorkBuddy 沙箱；Android SDK `E:\Code\Android\sdk`
- valid_since: 2026-09-13
- last_verified: 2026-09-13
- status: active
- root_cause: 两类操作必须在沙箱外执行：① **Gradle/Maven 依赖解析** —— 沙箱内 `dl.google.com` / `maven.google.com` / `repo1.maven.org` 均返回 **HTTP 200 但 0 字节**（传输被阻断），同一 URL 脱离沙箱后正常（实测 2361 字节）；② **Android 模拟器** —— 沙箱内 `emulator.exe` 启动后进程被立即杀掉（`emu.log` 为空、`adb` 报 `protocol fault (couldn't read status): connection reset`、`adb devices` 无设备）。
- prevention:
  1. 所有 Gradle 构建、模拟器启动一律走**非沙箱**通道；
  2. 模拟器**必须**把「启动 → `wait-for-device` → 等 `boot_completed=1` → `adb install` → `am start` → 验证」放在**同一条非沙箱命令**里串行执行；不能"先起模拟器、再单独装"——后台子进程会随命令结束被回收；
  3. 无窗口 CI 配置：`emulator -avd <name> -no-snapshot -no-boot-anim -no-audio -no-window -gpu swiftshader_indirect`（实测 `boot_completed=1` 约 20 秒，第 5 次探测）；
  4. **每次 Bash 调用都是新 shell，变量不保留** —— `export JAVA_HOME=...` 必须与使用它的命令写在同一条里，否则会出现"设了 JBR 21 却仍显示 JDK 24"的假象（直接用 `which -a java` 复核）。
- evidence: 沙箱内 Maven 探测 `http=200 bytes=0` vs 非沙箱 `bytes=2361`；沙箱内 `emu.log` 为空 + `adb` protocol fault；非沙箱同一链路全通
- revalidation: 2026-09-13 —— 非沙箱单命令链路：设备 `emulator-5554 device`、安装 `Success`、`topResumedActivity=com.thunderspike.demo/.MainActivity`、崩溃日志为空
